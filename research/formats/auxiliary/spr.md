# Specification: .SPR Sprite Bitmap Format

## 1. Overview & File Identification

The `.SPR` format represents uncompressed 8-bit indexed raster billboard images and animation frames developed for *Stunt Island*. The format was codified by Dave Palmowski (2001, Stunt Island Filmmakers Association / SIFA) with the release of the `SpriteMaker` suite (`PCX2SPR.EXE`, `MAKESPR.EXE`, and `DRAWSPRT.EXE`), enabling community filmmakers and modders to inject custom camera-facing billboard visual effects (explosions, smoke clouds, muzzle flashes, rocket flares, dynamic logos, and the Death Star easter egg) into the engine.

- **File Extension:** `.SPR`
- **Magic Bytes:** None. The file begins with three 16-bit little-endian words: width, height and encoding.
- **Typical Container / Storage:** Packaged as binary entries (`bin file.spr`) inside custom `.RES` archives (e.g. `MYSPRITE.RES`) generated by `MAKERES.EXE`.
- **Byte Endianness:** Little-endian (standard x86 16-bit real mode).
- **Engine Lifecycle Role:**
  1. *Raster Texture Storage:* Contains raw 8-bit VGA Mode 13h palette indices formatted for rapid scanline blitting into the $320 \times 200$ VGA video buffer.
  2. *Procedural Billboard Binding:* Bound to procedural `.SOD` (display list) models compiled by `MAKESPR.EXE`. The `.SOD` model defines the spatial transform, billboard orientation vector, animation frame count, and resource indices, while the `.SPR` payload supplies the raw texel colors.
  3. *Dynamic Visual Effects:* Rendered as camera-facing billboards centered at the entity's 3D origin, with index `0` acting as a strict transparency key.

**Governing invariants:** [`[I1]`](../../../docs/SPEC.md#i1-metric-right-handed-coordinates-attribute-preserving-vertex-welding--anglefov-normalization), [`[I3]`](../../../docs/SPEC.md#i3-authentic-vga-mode-13h-palette-indexing--flat-shading), [`[I5]`](../../../docs/SPEC.md#i5-coplanar-decal-resolution). **Contract and code:** [`contracts/shape.rs`](../../../crates/stunt-core/src/contracts/shape.rs); palette scaling is defined once in [`palette-and-shading.md`](../concepts/palette-and-shading.md#11-vga-hardware-dac-principles). Synthetic raw and span-coded images are built in [`test_spr_schema.py`](../../../tests/test_spr_schema.py); [`sprite.rs`](../../../crates/stunt-core/src/sprite.rs) reads `OP_ANIMATE` frames.

## 2. Header & Memory Layout

An image is three header words, width, height and an encoding word, then its body from byte 6: raw rows when the encoding word is 0, span-coded rows otherwise. There is no trailer. The executable layout is [`spr.ksy`](spr.ksy); the community `PCX2SPR` tool writes a different one (§ 2.3).

### 2.1 Encodings

* **Raw** (encoding 0): palette indices row by row, so the size is `width × height + 6`.
* **Span-coded** (any other value; the game's images carry 2): each row is a list of spans of pixels placed at a column (`span_row` in [`spr.ksy`](spr.ksy)). Columns no span covers are not drawn.

### 2.2 Field Definitions (`# [FMT-SPR-HEADER]`)

**The game reads pixels from byte 6.** `[Established]` for `PLAYONE`, static: its unscaled draw tests the word at byte 4 (`0x7C2E`), copies raw rows on 0 (`0x7C39`) and walks spans otherwise (`0x7CBA`); the `OP_ANIMATE` blitter (`0x7DE6`) ignores the word and reads raw rows ([`sod-animate.md`](../../playone-exe/sod-animate.md) § 3). `STUNT.EXE` and `MAKEONE.EXE`, unpatched and Patch #3, carry the same flag test, entry points and scaled-blitter opening bytes, and a loader that places the chunk the same way (`[Supported Inference]`: byte sequences matched, not traced from a caller). The corpus's `.RES` and `.ALL` archives, deduplicated by content, hold 125 raw images (`[Bounded Observation]`), 50 of which end in a non-zero word, so there is no trailer; they include `f0.spr`, a `PCX2SPR` sample whose first two pixels are 0 (§ 2.3). Of the 93 chunks with screen-sized dimensions, a non-zero word at byte 4 and another size, 58 read as span-coded images to exactly their end (`FASTSPR.RES` 8, `SPRITES.RES` 50, all with encoding 2); the other 35 were not identified. `0x7C2E` tests only for zero; in the game's archives no encoding but 0 and 2 occurs.

_Source: [where an SPR image's pixels start](../../../work/2026-11/481_spr-pixel-start/journal.md#2026-11-14-where-an-spr-images-pixels-start)._

### 2.3 `PCX2SPR` Output

`PCX2SPR` (SpriteMaker) writes width, height, the `width × height` pixels from byte 4, then a zero word: `MACLOGO.SPR` and `DSTAR.SPR` equal their `.PCX` sources' pixels from byte 4 byte for byte, and `dethstar.spr` differs from its source in 74 bytes read from byte 4 against 114,387 from byte 6 (`[Bounded Observation]`, three samples with sources). `DSTAR.SPR`'s copy is item `0x1E00` of the community `SITools/GameReady/Death.RES.RES`. The sizes agree (`width × height + 6`), but the game reads the first two pixels as the encoding word. Through `OP_ANIMATE`, the route `MAKESPR` models take, such a sprite is therefore drawn two pixels to the left, each row ending with the next row's first two pixels and the last row with the zero word (`[Hypothesis]`: read from the code, not observed in a capture). The schema sweep reports the three non-zero samples as known anomalies.

## 3. Data Structures & Opcode Table

### 3.1 Pixel Payload & Row-Major Addressing

A raw image's pixels run from the top-left corner $(0, 0)$ row by row to the bottom-right $(W-1, H-1)$ ([`spr.ksy`](spr.ksy)). Each byte is an index into the active 256-colour VGA Mode 13h palette.

### 3.2 Color Index 0 Transparency Key

- **Transparent Pixel:** Palette index `0x00` (`0`) is transparent where the blitter keys it: the scaled `OP_ANIMATE` blit (`0x7DE6`) stores only non-zero bytes. `PLAYONE`'s unscaled draw does not key it: raw rows are copied whole (`rep movsb` at `0x7CA7`), and span-coded rows copy every byte of a span, leaving only the columns no span covers untouched (`[Established]`, static; § 2.2). Our renderer draws `OP_ANIMATE` sprites as that blit does: texels with index `0` are discarded (transparent keying / alpha mask test `alpha = 0.0`), allowing background 3D scenery and skyboxes to show through without overdraw.
- **Opaque Pixels:** Palette indices `0x01` through `0xFF` (`1..=255`) represent visible, opaque surface colors.

### 3.3 Procedural `.SOD` Billboard Coupling

A `.SPR` bitmap is never rendered in isolation; it is referenced by a procedural `.SOD` (display list) model compiled by `MAKESPR.EXE`. The compiled `.SOD` binary (typically 48 bytes for single-frame billboards, such as `DETHSTAR.BIN`, `DSTAR2.BIN`, `MAC500.BIN`, `MINE.BIN`) contains the following bytecode sequence:

| Offset | Size (Bytes) | Value / Opcode | Symbolic Name | Function |
| :--- | :--- | :--- | :--- | :--- |
| `0x00`–`0x01` | 2 | `0x000C` | `OP_ID` | Standard SOD header identifier |
| `0x02`–`0x03` | 2 | `u16` | `bounding_size` | Model bounding sphere radius |
| `0x04`–`0x05` | 2 | `0x0000` | `y_offset` | Vertical ground offset |
| `0x06`–`0x07` | 2 | `u16` | `scale_factor` | Initial scale factor (commonly `4000` or `0x0FA0`) |
| `0x08`–`0x09` | 2 | `0x0000` | `collision` | Collision sphere descriptor |
| `0x0A`–`0x0B` | 2 | `0x0075` | `OP_VECTORS` | Subobject vector definition table |
| `0x0C`–`0x2B` | 32 | Bytecode stream | Billboard Transform | Billboard orientation opcodes constraining normal to face camera eye |
| `0x2C` | 1 | `u8` | `frame_index` | 0-based frame index within the target `.RES` archive |
| `0x2D` | 1 | `u8` | `res_archive_id` | Resource archive index ID containing the `.SPR` files |
| `0x2E`–`0x2F` | 2 | `0x0195` | `OP_END` / `OP_RETURN` | Bytecode termination sentinel |

### 3.4 Animation Frame Cycling

When multiple `.SPR` frames are bound to a dynamic billboard object, `MAKESPR.EXE` compiles an animation sequence table:
- The total duration of the animation cycle remains constant across simulation ticks.
- The display duration per frame is inversely proportional to the frame count:
  $$\Delta t_{\text{frame}} = \frac{T_{\text{cycle}}}{N_{\text{frames}}}$$
- The playback engine indexes frames cyclically:
  $$\text{current\_frame}(t) = \left\lfloor \frac{t}{\Delta t_{\text{frame}}} \right\rfloor \pmod{N_{\text{frames}}}$$

### 3.5 Billboard Quad Geometry (`[I1]`)

Per Invariant `[I1]`:
- Sprites are authored as symmetric planar rectangles centered at local coordinate $(0.0, 0.0, 0.0)$.
- The four quad corner vertices in local space span:
  $$v_0 = \left(-\frac{W}{2} s, +\frac{H}{2} s, 0\right), \quad v_1 = \left(+\frac{W}{2} s, +\frac{H}{2} s, 0\right)$$
  $$v_2 = \left(+\frac{W}{2} s, -\frac{H}{2} s, 0\right), \quad v_3 = \left(-\frac{W}{2} s, -\frac{H}{2} s, 0\right)$$
  Where $s$ is the metric world scale multiplier derived from the `.SOD` scale word.
- In camera-facing billboarding, the quad's normal vector $\mathbf{n}$ is dynamically aligned with the inverted camera view direction:
  $$\mathbf{n}_{\text{quad}} = \frac{\mathbf{P}_{\text{cam}} - \mathbf{P}_{\text{sprite}}}{\|\mathbf{P}_{\text{cam}} - \mathbf{P}_{\text{sprite}}\|}$$

### 3.6 Billboards vs. Coplanar Decals (`[I5]`)

Unlike coplanar decals which require normal displacement ($\epsilon = 0.001\text{ m}$) against underlying mesh faces (`[I5]`), `.SPR` billboards exist as standalone 3D volumetric proxies with distinct depth buffer writes and alpha testing.

## 5. Attribution & Provenance

The technical specifications and byte layouts for the `.SPR` format are synthesized from the following primary community research and tooling archives:

- **Dave Palmowski (2001):** Author of the `SpriteMaker` package, designer of `PCX2SPR.EXE`, `MAKESPR.EXE`, and author of the authoritative format manual (`corpus/siarchive/SITools/SpriteMaker/sprite.txt`, `corpus/siarchive/SITools/SpriteMaker/Dstar.txt`).
- **SIFA (Stunt Island Filmmakers Association):** Preservation of sprite creation toolsets, palette files (`si.pal`, `si.act`), and community sample sprites (`dethstar.spr`, `f0.spr`, `MACLOGO.SPR`).
- **Adrian Stephens (The Assembly Line, 1992):** Original Stunt Island assembly engine architecture and billboard display list mechanics.
- **Stunt Reel contributors (2026):** The encoding word and span-coded rows from `PLAYONE.EXE`, the `PCX2SPR` byte-4 layout, integration with `Seam 3: SodModelIr`, and documentation of Mode 13h palette index preservation `[I3]`.
