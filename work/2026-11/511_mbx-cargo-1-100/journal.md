# Journal: Is mbx usable for worktree `target/` seeding on Cargo 1.100? (#511)

## 2026-11-14: mbx 1.30.0 against the block-clone seed, first `check-rust` of a fresh worktree

- **Question**: On Cargo 1.100.0, does a fresh worktree's first `mise run check-rust` finish faster with `mbx` (mr-boxington) and a warm store than with `mise run init`'s seed (which, since #486, keeps unchanged workspace units), and does `mbx` meet the three gates of [spec § 7](../target-seeding/spec.md) (restores clone on ReFS, `CARGO_TARGET_DIR` honoured, workspace crates restore or cold Rust lanes beat the seed)?
- **Method**: On `E:` (ReFS Dev Drive), origin/main `0c92e962` (seed from #486, `rust-toolchain.toml` 1.100.0), no cargo, rustc, clippy-driver or rustdoc process before any timed run (`Get-Process` count 0 each time; top CPU processes were the Radeon software and Orca). `mbx` 1.30.0 (newest release, 2026-11-09), the `x86_64-pc-windows-msvc` zip from `jdx/mr-boxington` with its `SHA256SUMS` checked, run from a scratch folder, not installed; a mise-installed 1.27.0 sits unused in mise's tool folder from before.
  - (a) Current seed: donor A, a fresh worktree built by `mise run check-rust` twice (34 s, then 11 s). Each run used a new worktree (B, B2, B3), `git worktree add --detach`, with A's `target/debug/.fingerprint` and `target/debug/build` times set to now (donor-tie bug #521), `mise run init` (all three: "target/ seeded from" A), then a timed `mise run check-rust`.
  - (b) `mbx`: store at `E:\mbx511-store` (`MBX_CACHE_DIR`; no `mbx setup`, no global config file written), cargo routed through `mbx` by an untracked `mise.local.toml` holding the line `mbx setup --local` writes, `wrappers = { cargo = { command = "mbx", env = { MBX_CARGO_SHIM_MODE = "1" } } }`. Fill run: worktree F, a `stunt-core` lib build, then `mise run check-rust` on an empty store. Timed runs: fresh worktrees G2, G3 and G4 (G1 was spoiled by an extra untimed workspace build and not counted); each `ensure` would otherwise seed an empty `target/` from A and so hide `mbx`, so a pre-step `cargo build --locked -p stunt-core --lib` through the wrapper first made `mbx` create the managed `target` symlink (timed separately), then a timed `mise run check-rust`.
  - Times are the gate's own "PASS 5/5 steps in N s"; wall-clock for the `mbx` runs is in the table. Units built are `Compiling`, `Checking` and `Documenting` lines in `target/check.log`. Disk is the drop in `E:` free space, read after the seed or pre-step and after the gate; other processes wrote to `E:` meanwhile, so it is a rough bound (one `mbx` run read negative).
- **Result**:
  - `mbx doctor`: restores clone on `E:` ("cloning is supported" for the store to the managed targets and to the checkout's `target`) only when the store is on `E:`. Its default store, `C:\Users\Steam\AppData\Local\mbx`, reports "cannot clone or link; every restored byte is copied" for a checkout on `E:`; `MBX_CACHE_DIR` fixes it. Other warnings: `ar` and `llvm-ar` absent (archive determinism unprobed), `E:` does not refresh access times (unused-unit collection skipped), and the shim not on `PATH`.
  - `CARGO_TARGET_DIR` (`target/check`, `target/matrix`, ADR 0016) is honoured: the lanes sit inside the managed `target`, a symlink into the store (`target -> /e/mbx511-store/targets/v1/<hash>`). `CARGO_INCREMENTAL=0` and the per-task `CARGO_HOME` worked through the wrapper (no "Access is denied"); `target/debug/incremental` was empty.
  - Fill run (empty store, first worktree): 68 s (381 units, `E:` free space down about 2.0 GB, store 3.6 GB by `du`), no faster than the 62-64 s unseeded gate of ADR 0017.
  - `mbx` seeds a new target itself ("copied 512 registry build units from" the previous worktree), but rebuilds the workspace crates: 26-34 units, against the seed's 13.

  Disk added after the gate (rough): seed 168-427 MB beyond a 374-807 MB init; `mbx` 235-430 MB (one reading negative), so no clear disk difference.
  - Interactions: `mise run clean` in an `mbx` worktree reports `target` as 0.0 MiB, so it cannot see or free the managed store; `mbx` keeps that space under its own gc (45 GiB default budget, 5 GiB here after `MBX_CACHE_DIR` on a small drive). `mise run reap` was not exercised against a managed `target`. Making `mbx` apply needs a `mise.local.toml` wrapper or `mbx setup`, which writes the cargo shim under `%LOCALAPPDATA%\mbx\bin` and a new `rust-analyzer.toml`; both were removed afterwards.
- **Verdict**: rejected, by the third gate. Spec § 7's gates: (1) restores clone on ReFS, met with the store on `E:`, not with the default `C:` store; (2) `CARGO_TARGET_DIR` honoured, met; (3) workspace crates restore or a second worktree's cold Rust lanes beat the seed, not met: the workspace crates rebuild (26-34 units against 13) and the lanes took a median 20 s gate (22.7 s wall, 30.8 s with the pre-step that stands in for `ensure`) against the seed's 15 s; they beat the 40 s the gate named when written, not the seed's current figure. The filled-store cost is 68 s once. ADR 0017 and the seed stand; there is no ADR to supersede it.
