# Toolchain, dependencies and shared caches

## Shared tool cache

`mise.toml` points `UV_CACHE_DIR` at the primary checkout's `.cache/uv`, and the cargo tasks' `CARGO_HOME` at its `.cache/cargo`, both by absolute path, so every worktree reuses one set of downloaded crates and uv artifacts with no link. Build outputs (`target/`) and the Python tool caches stay per worktree, because they are revision-specific or not relocatable.

On a ReFS volume, the hidden `ensure` task, which every task that builds Rust runs first, seeds an empty `target/` by cloning another checkout's build output under a lock (`mise run init` and `mise run seed` do it on demand): the clone shares disk blocks with its donor, every dependency arrives fresh, and a workspace crate's unit is kept only where every file it was built from is byte-identical to the donor's and Cargo records none of them by the donor's absolute path; a unit whose Cargo record names the donor's path rebuilds, which on 2026-11-14 covered the clippy units (they record `clippy.toml` and `Cargo.toml`) and the test units that embed files under `tests/fixtures/`. A new worktree's first Rust lanes took a median 18.5 s over four runs on 2026-11-14, against 23 s with the previous seed, which rebuilt every workspace crate. The donor must sit on the same drive (a clone cannot cross volumes), be built by the same `rustc` against the same `CARGO_HOME`, and not be building; a clippy or matrix lane built otherwise is left out. It prints which donor it used or, when it fails, why it seeded nothing, and warns when `CARGO_HOME` is not the shared cache's own path. See [ADR 0030](adr/0030-new-worktrees-seed-target-by-block-clone.md).

Each worktree keeps uv's own `.venv`; on the cache's volume uv hardlinks the packages out of it, and on another volume (Orca's worktrees on `C:`) it copies them, about 68 MiB and 3 s. Worktrees an older `init` linked still hold a `.venv` junction into `<cache>/venvs/`; `reap` deletes a reaped worktree's environment there and `reap --prune` sweeps those whose checkout is gone. See [ADR 0013](adr/0013-worktrees-share-one-writable-tool-cache.md) and [ADR 0036](adr/0036-worktrees-reach-shared-state-by-configuration.md).

## Running individual commands

For a one-off that no task covers, run the pinned tool through mise: `mise exec -- uv run ruff check python/foo.py`. `mise exec` puts the versions [`mise.toml`](../mise.toml) pins on `PATH`; a bare `uv` can be a different version. `[tool.uv] required-version` in [`pyproject.toml`](../pyproject.toml) is a floor at the pin, not an exact match: an older uv refuses to run, a newer one runs. It cannot be exact because Renovate's `pep621` manager runs its own, newer uv and stops with `tool_version_not_supported` when the project names a different version; raise the floor whenever `mise.toml` raises the pin.

## Python dependencies

The Python half runs on the standard library unless a dependency earns its place. [ADR 0010](adr/0010-python-scripts-may-take-well-established-dependencies.md) holds the bar: wheels on every CI platform, typed, an acceptable licence, and a release within about two years, with the admitting ADR stating the job the dependency does and why the standard library cannot. The shipped `stunt_reel` wheel stays dependency-free; a tooling-only dependency belongs in the dev group, where `python/scripts/` can import it. pydantic, pydantic-settings and Typer were considered for the parity scripts and refused in that ADR. `jsonschema` and its typeshed stubs `types-jsonschema` are in the dev group for the parity conformance tests, admitted by [ADR 0048](adr/0048-the-python-parity-adapter-is-checked-against-a-generated-schema.md).

## Dependency updates

Renovate keeps every ecosystem current — crates, Python dev dependencies, GitHub Actions pinned to commit SHAs, the research site's Bun/npm packages, and the tools [`mise.toml`](../mise.toml) pins, which Dependabot could never reach. A dependency bot that cannot touch the toolchain is not managing the most consequential dependency in the tree: a crate bump changes one library, while a `rust` bump changes the compiler that produced every artifact and the verdict in the `msrv` job.

It runs as the Mend-hosted app rather than a self-hosted workflow. The allowed-actions policy admits GitHub-owned actions and the two third-party patterns [`ci.yml`](../.github/workflows/ci.yml) names, so self-hosting would mean admitting a third pattern and keeping a token or App key alive — for a job that is a schedule and an API client. The hosted app costs one file, [`.github/renovate.jsonc`](../.github/renovate.jsonc), and no repository secrets.

The rules that matter operationally:

- **Nothing auto-merges.** `msrv` and `deny` are the only enforcement of the Rust floor and the licence allow-list, and Renovate cannot read either: MSRV filtering for the `crate` datasource is undocumented in practice, and no option exists for a licence allow-list. Every bot PR runs the full gate like any other.
- **Groups split by what a failure implicates.** Patch and minor crate bumps share a PR; majors get their own, because a red `msrv` or `deny` should name one crate rather than hide behind a green action bump. Actions, Python dev dependencies and the mise pins have their own groups.
- **New releases wait three days** (`minimumReleaseAge`), and lock files refresh monthly (`lockFileMaintenance`): a yanked crate or a transitive advisory has no upgrade for `vulnerabilityAlerts` to propose, so the lock file needs a refresh that is not a version bump.
- **Two pins are frozen.** `kaitai_struct_compiler` carries a `sha256` of its release zip and the dosbox-automation entry names an `asset_pattern` and a `checksum`; for those a version bump alone installs nothing, and no gate run on any platform would catch it.
- **Security fixes still arrive.** Dependabot's alerts stay on and Renovate raises the fix PRs from them; Dependabot's own version and security updates are off, so one bot writes lock files and one raises advisories.

Three conventions keep the pins honest. A **pin** is what gets installed ([`mise.toml`](../mise.toml) `[tools]`, [`rust-toolchain.toml`](../rust-toolchain.toml)), and only a pin may move automatically. A **floor** is the minimum the project claims (`rust-version = "1.100"`, `requires-python = ">=3.15"`), and moving one is a deliberate act after `msrv` proves it. A **target** is what ruff and mypy assume, which Renovate cannot see, so a pin moves only when its targets move with it (mypy's target equals the pin; ruff's may trail it by one minor between an upgrade PR and its apply-ruff PR). The **interpreter** the gate runs on is the pin's minor: `python-preference` keeps uv on the Python mise puts on PATH, and only a `uv` run outside `mise` against a different PATH interpreter drifts from it. [`tests/test_toolchain_pins.py`](../tests/test_toolchain_pins.py) fails the gate if a pin, a floor, a target and the running interpreter drift apart — and that test is what lets the compiler stay declared in two files at all: `rust-toolchain.toml` resolves (rustup reports the active toolchain overridden by it) while `mise.toml` installs, so the two are one Renovate group and the test proves them equal.
