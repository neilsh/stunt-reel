# Quality gate and CI

The gate is `mise run check`: one script ([gate.py](../python/scripts/gate.py), [ADR 0014](adr/0014-the-gate-is-one-ordered-script.md) and [ADR 0016](adr/0016-the-gate-runs-independent-lanes.md)) that prints one line per step, quotes the tail of every failing step, writes the whole output to `target/check.log`, and ends with PASS or FAIL. Independent steps run as concurrent lanes — cargo steps that share a target directory stay in one ordered lane, everything else runs beside them — so one run also reports every failing step, not only the first. `mise run check-rust` and `mise run check-py` run the same step list for one language, and `mise run check-docs` runs only the documentation tests (`test-py-docs`, the modules marked `docs`). A failing run's last line says what to run next: `fix: mise run fix` when a format or `lint-py` step failed, and `re-run: mise run check-rust` / `check-py` / `check-docs` for the half that failed (a scoped run never names itself).

`mise run check` runs only what the branch touches ([ADR 0038](adr/0038-the-local-gate-runs-what-a-change-touches.md)). It reads the paths changed since the merge base with `origin/main` (with `main` when there is no `origin/main`), untracked files included, and sorts each one: `tests/fixtures/**` is other; `crates/**`, `Cargo.toml`, `Cargo.lock`, `deny.toml` and `research/parity/report-fields.md` (a Rust test reads it) are Rust; `*.py`, `pyproject.toml` and `uv.lock` are Python; `*.md` and `*.ksy` are docs; anything else is other. Rust paths run the Rust half, Python paths the Python half, and a run without the Python half adds the docs half. It runs the full gate, and prints why, on `mise run check -- --full`, when `CI` is set, for any other path, when nothing changed, and when git cannot say (neither `origin/main` nor `main`); `-- --base <ref>` counts from another branch. The gate prints its scope and the paths behind it first. CI's `quality` job always runs the full gate. Individual tasks:

The pre-commit hook is installed by `mise run init` (`core.hooksPath = .githooks`) and holds no command of its own: it runs `mise run pre-commit`, which is [prek](https://github.com/j178/prek) over [`prek.toml`](../prek.toml) ([ADR 0026](adr/0026-commit-hooks-run-the-gates-own-tasks.md)). prek sets unstaged edits aside first, so the hooks check what is being committed. Its local hooks are leaf tasks of `mise.toml` — `diff-check`, `crlf-check` (CRLF in a staged text file's working copy, which `.gitattributes` would normalise away but the format check still reads; repaired when that is the only difference), `test-docs` and `check-work-frozen` (a file added to a frozen work folder, or its outcome changed) on every commit, `fmt-check-rust` when Rust is staged, `fmt-check-py` and `lint-py` when Python is — so they cannot drift from the gate the way the deleted `.pre-commit-config.yaml` did; the rest are prek built-ins (large files, Windows-illegal names, case conflicts, merge conflicts, TOML and YAML syntax, private keys). No hook changes what is committed, and `crlf-check` alone writes a file, one git already sees as unchanged: `mise run fix` (or `mise run fmt`, which only formats) fixes a format failure. It catches what commits most often broke (conflict markers left by a rebase, broken doc links) in seconds; it does not replace `mise run check` before a commit, and CI runs the built-ins on every pull request and push to `main`. Setting `core.hooksPath` turns off untracked hooks in `.git/hooks`, so `.githooks/pre-commit` and `.githooks/pre-push` chain to one there if present, and `init` names any other it turns off. `git commit --no-verify` skips the hook once.

The gate's lanes build the check profile into `target/check` and the no-default-features matrix into `target/matrix`, so those builds can run beside the `target/` build instead of waiting on its lock. All three directories sit under `target/`, which `.gitignore`, ruff's exclude, the recursive walkers and `mise run clean` already cover.

CI ([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)) invokes the mise tasks instead of restating them. Every pull request runs the full `mise run check` gate on Ubuntu, with Mesa's lavapipe installed and `STUNT_REQUIRE_GPU=1` set so a missing adapter fails the GPU tests instead of skipping them ([ADR 0006](adr/0006-ci-renders-on-lavapipe.md)), and `check-windows-smoke` on Windows for the tests that can behave differently there. Windows gets a smoke test rather than the whole gate on pull requests because every Windows-only behaviour in this repository lives in the Python tree — `crates/` has no `cfg(windows)` — while a warm Windows Rust build costs about nine minutes. Pushes to `main` run the full `check-windows` too (format, lint, typecheck and both test suites; GPU tests skip without a driver), and `workflow_dispatch` runs every job on any branch. A separate job checks the declared MSRV (`1.100`), and a `cargo deny` job enforces the dependency policy; both run on every pull request and push rather than being path-filtered, since the runners are free once the repository is public. The cargo cache falls back to the newest previous lockfile through `restore-keys`, so a dependency bump rebuilds a delta instead of the whole workspace — a cold gate run measured 10m40 against 4m19 warm. Each job installs only the toolchain its task list uses (`rust`, `python`, `uv`, and Java with the Kaitai compiler where `test-py` runs), because `mise run` otherwise installs every tool `mise.toml` declares before its first task — compiling `cargo-deny` and `cargo-llvm-cov` from source and downloading DOSBox inside the gate — so the jobs set `MISE_AUTO_INSTALL=false`. Corpus- and emulator-dependent tasks stay local. A ruleset on `main` requires the four jobs that run on every pull request — `quality`, `windows-smoke`, `msrv` and `deny` — and blocks force pushes and deletion; repository admins may bypass it to push straight to `main`. ## GPU tests

The `gpu` test binary (`crates/stunt-render/tests/gpu/`, kept apart from the merged `it` binary so the watchdog can run it alone) exercises the Vulkan/DX12/GL loader and vendor driver locks, and a wedge there leaves a plain `cargo test` waiting forever without printing a result; [run it under the watchdog](howto/run-the-gpu-tests.md). Every test in it wraps its body in `common::gpu_test`, which holds one process-wide lock and runs the body on a thread it joins before releasing the lock; opening a renderer outside it panics. The join is the point (`[Bounded Observation]`, one NVIDIA RTX 4070 laptop): a thread that had used NVIDIA's OpenGL driver (`nvoglv64.dll`, reached through the software-only adapter's all-backends instance, or a dropped GL instance's `wgpu-hal WGL Instance Thread`) and exited after the lock was released ran its `DllMain` detach holding the loader lock, and deadlocked against the next test's Vulkan `request_device` loading a DLL (12 hangs in 150 runs without the join, none in 200 with it). For the same reason a test that builds its own `wgpu::Instance` leaves out `Backends::GL`: wgpu ends the WGL thread after the instance drops, outside any lock. _Source: [2026-11-07: GPU tests hang on an NVIDIA laptop](../work/2026-11/distill-development/journal.md#2026-11-07-gpu-tests-hang-on-an-nvidia-laptop)._

## A PermissionError on Windows

On this machine's Dev Drive (`E:`, ReFS), the gate now and then fails a Python test with `PermissionError: [Errno 13] Permission denied` or `[WinError 5] Access is denied` on a file the test does not hold, and a rerun passes. The test does not matter: it has been a tracked file untouched for an hour (`manifests/all/*.toml`, `python/scripts/*.py`), a file or directory under the pytest basetemp, or a scratch repository's `.git/config` read just after `git config` wrote it. A plain `git switch -c` outside pytest was once refused the checkout's `.git/config` the same way. Session transcripts hold 43 such minutes between 2026-10-29 and 2026-11-09, across many worktrees, under both `mise run check` and `mise run regate` (`[Bounded Observation]`).

What holds the file is not yet named. Ruled out: `regate`'s checkout racing the tests (git finishes the checkout before the gate starts, no `post-checkout` hook runs, and the plain gate fails the same way), the basetemp pruning in `tests/pytest_helpers.py` (it keeps the three runs with the newest UTC-stamped names, so it deletes a live run only if three or more later runs start in the same checkout while it runs, and one gate starts two; and the sampled tracked files have one link each), a gate in another worktree (none was running at the 2026-11-09 failures), a sandbox ACL (the worktree carries only inherited ACEs, and the token no restricted SID), the search indexer (Windows Search returned no indexed items under `E:` when queried on 2026-11-09), and ReFS keeping a deleted file's name (on the Dev Drive, a file deleted while another handle had it open with `FILE_SHARE_DELETE` lost its name at once, as on NTFS). It did not recur on demand: 4 full gates, 9 `regate` gates and 4 pairs of concurrent pytest runs passed while a watcher polled 282 files for a refused open, and in another worktree 6 full gates and 9 concurrent `test-py` plus `test-py-docs` runs passed too. Defender's operational log shows nothing at either failure, but its exclusions and scan activity need admin to read, so a scanner holding a file is neither confirmed nor ruled out. Windows Security Center lists no antivirus besides Defender, but it does not list every filter driver, such as backup or sync software.

The pruning did have a defect of its own, now fixed. `shutil.rmtree(ignore_errors=True)` could not delete git's read-only object files, so every run's basetemp stayed behind (102 in one worktree), and every xdist worker walked all of them again at start-up. The prune now clears the read-only bit, and only the controller runs it.

When a test fails on a `PermissionError`, `tests/conftest.py` asks the Restart Manager which processes hold each path the error names and adds a `file holders` section to the failure report. It sees a holder only while it still holds the file, and a file pending delete shows as held by no process. Copy that section onto [#260](https://github.com/neilsh/stunt-reel/issues/260) before rerunning. _Source: [#357](https://github.com/neilsh/stunt-reel/issues/357)._

## `stunt-core` test kinds

`stunt-core` tests come in three kinds. Named single inputs with exact expected results go in the `*_spec.rs` and `*_test.rs` files. Never-panics checks over random or mutated bytes are the fixed-seed `XorShift64` loops in the `*_fuzz.rs` files. A property that must hold for every valid input goes in a `*_props.rs` file, or in a `props` module beside the crate-private code it tests: write then read gives back the input, two implementations of one rotation agree, sampling at a keyframe returns that keyframe. These use [proptest](https://docs.rs/proptest), which builds constrained inputs (unit quaternions, timelines with same-tick slices) from composable strategies and shrinks a failure to a minimal case. Each runs 256 cases from a fixed seed, so the gate sees the same cases every run; setting `PROPTEST_CASES=10000` or `PROPTEST_RNG_SEED=<n>` for a `mise run test-rust` explores further without an edit. No regression files are written: when a property fails, add its shrunk input to the matching spec file as a named test, then fix the code or the property.
